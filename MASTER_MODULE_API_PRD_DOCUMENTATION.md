## 🎯 Overview

The Master Module manages the complete Chart of Accounts (COA) and ledger system. It follows standard double-entry accounting principles where every transaction has equal debits and credits.

**Key Features:**
- Hierarchical account structure (Root → Folder → Subfolder → Account)
- Automatic GL code generation based on parent account
- Real-time balance calculation across all ledgers
- Balance aggregation from child accounts to parent (hierarchical rollup)
- Support for Assets, Liabilities, Income, and Expenses

**Data Storage:**
- All data stored in browser's localStorage
- Key stores: `chartOfAccounts`, `transactions`, `ledgerBalances`

## 🌳 Account Structure & Hierarchy

### Account Type Levels

```
ROOT (Level 0)
  ├── FOLDER (Level 1)
  │     ├── SUBFOLDER (Level 2)
  │     │     ├── SUB-SUBFOLDER (Level 3)
  │     │     │     └── ACCOUNT (Level 4+)
  │     │     └── ACCOUNT (Level 3+)
  │     └── ACCOUNT (Level 2+)
  └── ACCOUNT (Level 1+)
```

**Account Types:**
- **ROOT**: Top-level categories (A, L, R, X)
- **FOLDER**: Main groups under root
- **SUBFOLDER**: Sub-groups under folders
- **SUB-SUBFOLDER**: Further subdivisions
- **ACCOUNT**: Final ledger where transactions are posted

> **Note:** Account type (ROOT/FOLDER/SUBFOLDER/ACCOUNT) should be automatically determined by the backend based on the hierarchical structure and parent account type. This ensures consistency in the chart of accounts.

### Four Main Roots

```
A - ASSETS
L - SOURCES OF FUNDS (Liabilities)
R - INCOME
X - EXPENSES
```

### GL Code Generation Rules

1. **For ROOT accounts**: Single letter (A, L, R, X)
2. **For FOLDER**: Root letter + 4 digits (e.g., A1001, L2002)
3. **For SUBFOLDER**: Parent code + 3 digits (e.g., A1001001)
4. **For ACCOUNT**: Parent code + 3 digits OR Parent code + suffix
5. **Special cases**: 
   - Employee ledgers: Parent + "-EMP-" + employee_id
   - Vendor ledgers: Parent + "_VEN_" + vendor_id
   - Client ledgers: "D" + sequence (D001, D002)

**Backend Logic Required:**
- Get parent account's GL code
- Count existing children under parent
- Generate next sequence number
- Append to parent code following the pattern

## 17. Specialized Ledger APIs: Bank Ledgers (A3004)

The Bank Ledger is the liquid control layer of the accounting module. It records all outgoing payments (credit to bank asset) and incoming receipts (debit to bank asset). Any posted transaction line touching `A3004*` accounts must be traceable here.

### 17.0 Scope Boundary (Current Phase)

To keep this phase implementation-safe, this section excludes dependency on expense-head-level enrichment.

- Included now:
  - Bank header metadata
  - Ledger rows with running balance
  - Footer totals
  - Voucher, counterparty, status, and dimension fields
- Deferred to next phase:
  - Expense-head driven enrichments and category-level analytics
  - Deep payment instrument workflows beyond ledger posting view

### 17.1 Data Sourcing and Integration Rule-set

Accounting sign convention for Bank (Asset):

- `Debit` increases bank balance (money in)
- `Credit` decreases bank balance (money out)

| Ledger Column | Source Module | Backend Rule |
|---|---|---|
| Date | Accounts | Date when transaction is posted to ledger (posting date, not UI draft date). |
| Voucher No | Accounts | Generated only on explicit approval/posting by authorized approver. |
| Voucher Link | Accounts/Documents | Nullable URL to immutable signed voucher document. May be `null` if document service is not enabled yet. |
| Entry Type | Accounts | Strict derived enum: `PAYMENT` when bank line is credit, `RECEIPT` when bank line is debit, `OPENING` for opening row. |
| Debit (INR) | Accounts | Amount for incoming bank movement (receipt). |
| Credit (INR) | Accounts | Amount for outgoing bank movement (payment). |
| Balance (INR) | Accounts | Chronological running value: `Opening + Debit - Credit`. |
| Narration | Accounts | Ledger narration from posted bank-side line, fallback to transaction narration. |
| Ref No | Accounts/Bank Integration | Prefer UTR/Bank Txn Ref when available; fallback to source transaction reference id. |
| Counterparty | Accounts | Must resolve to opposite-side ledger in same journal/transaction. |
| Approved By | Security/Auth | Final approver who posted/authorized voucher. |
| Status | Accounts | Lifecycle state: `POSTED`, `RECONCILED`, `REVERSED`, `VOIDED`. |
| Cost Center / Customer / Site / State | Accounts Dimensions | Dimensions inherited from root transaction or line-level overrides. |

### 17.5 Edge Cases and Production Fault Tolerance

Backend must enforce the following:

1. Negative balance (overdraft):
   - If running/closing balance `< 0`, set `isOverdraft=true` in row/footer payload.

2. Missing counterparty integrity:
   - If opposite ledger line cannot be resolved, return fallback `counterparty="UNCATEGORIZED_LEDGER_ERROR"` (do not break response).

3. Invalid date range:
   - If `fromDate > toDate`, return `400 BAD_REQUEST`.

4. Reversal and void handling:
   - Never delete original posted row.
   - Post explicit reversal row with opposite sign and `status="REVERSED"`.
   - Link reversal row to original voucher/reference.

5. Immutable voucher numbering:
   - Once posted, `voucherNo` cannot be edited.
   - Corrections must be performed through reversal/rebook entries.

### 17.6 Validation and Error Codes

| Scenario | Endpoint | Error Code | HTTP |
|---|---|---|---|
| Invalid/non-bank GL code | `/ledger/bank/:glCode/*` | `INVALID_BANK_GL_CODE` | 400 |
| Non-postable bank node | `/ledger/bank/:glCode/*` | `BANK_GL_NOT_POSTABLE` | 400 |
| Date range invalid | `/ledger/bank/:glCode/entries` | `INVALID_DATE_RANGE` | 400 |

## 💰 Balance Calculation

### Overview
Balances are calculated in real-time from transactions and aggregated up the hierarchy.

### Calculation Logic

**For Individual Accounts (Leaf nodes):**

```
Balance = SUM(Debit Entries) - SUM(Credit Entries)

- Debit entry increases the debit side
- Credit entry increases the credit side
- Display balance as absolute value with DR/CR indicator
- DR (Debit) when debit total > credit total
- CR (Credit) when credit total > debit total
```

**For Parent Accounts (Folders/Subfolders):**

```
Parent Balance = SUM(All Child Account Balances)

Aggregate all child account balances to parent level
Maintain DR/CR designation based on net calculation
```

### Balance Display Rules

1. **At Account Level:**
   - Show calculated balance from transactions
   - Display as: "₹1,25,000.00 DR" or "₹50,000.00 CR"

2. **At Folder Level:**
   - Sum all child account balances
   - Display aggregated total

3. **At Root Level:**
   - Sum all child folder/account balances
   - Display total for that account type (Asset/Liability/Income/Expense)

### Example Hierarchy Balance

```
A - ASSETS (₹50,00,000.00 DR)
  ├── A1 - FIXED ASSETS (₹10,00,000.00 DR)
  │     ├── A1001 - FA COMPUTERS (₹2,50,000.00 DR)
  │     └── A1002 - FA FURNITURE (₹7,50,000.00 DR)
  └── A3 - CURRENT ASSETS (₹40,00,000.00 DR)
        └── A3004001001 - HDFC Bank (₹40,00,000.00 DR)
```

## 📊 Account Types

### 1. ROOT
- **Purpose**: Top-level categorization
- **Codes**: A, L, R, X
- **Cannot have transactions**: Only for grouping
- **Balance**: Sum of all children

### 2. FOLDER
- **Purpose**: Major account groups
- **Examples**: FIXED ASSETS (A1), CURRENT LIABILITIES (L2002)
- **Cannot have transactions**: Only for grouping
- **Balance**: Sum of all children

### 3. SUBFOLDER
- **Purpose**: Sub-groupings under folders
- **Examples**: EMPLOYEE ADVANCE (A3001001)
- **Cannot have transactions**: Only for grouping
- **Balance**: Sum of all children

### 4. SUB-SUBFOLDER
- **Purpose**: Further subdivisions
- **Can have transactions**: Depends on structure
- **Balance**: Sum of children OR own transactions

### 5. ACCOUNT
- **Purpose**: Actual ledger where transactions post
- **Examples**: FA COMPUTERS (A1001), HDFC Bank (A3004001001)
- **Must have transactions**: Direct posting
- **Balance**: Calculated from its own transactions

- For each transaction: SUM(debits) must equal SUM(credits)
- debit and credit cannot both be > 0 in same entry
- glCode must exist in chart of accounts
- glCode must be of type ACCOUNT (cannot post to folders)

### 1. Account Creation

- ✅ GL code auto-generated by backend
- ✅ Cannot create duplicate GL codes

### 2. Account Deletion
- ✅ Cannot delete if has child accounts (must delete children first OR cascade delete)
- ✅ Cannot delete if has transactions (recommend making inactive instead)
- ✅ Must confirm before deletion
- ✅ Log deletion for audit trail

### 3. Transaction Posting
- ✅ Debit = Credit (balanced entry)
- ✅ Can only post to ACCOUNT type (not folders)
- ✅ Cannot post to future dates
- ✅ Voucher number must be unique
- ✅ Must specify narration
- ✅ Must have approval

### 4. Balance Calculation
- ✅ Real-time calculation from transactions
- ✅ Aggregate child balances to parent
- ✅ Cache results for performance
- ✅ Sync on transaction create/update/delete

### 5. GL Code Generation
- ✅ Follow Maxus standard format
- ✅ Sequential numbering within parent
- ✅ Handle gaps in sequence
- ✅ Special formats for employees/vendors/clients

### 14.6 Update / Rename Account API

**Endpoint:** `PUT /api/v1/master/accounts/:id`

**Purpose:** Renames account and/or updates parent (as per policy).

**Immutability Rule:** `code` (GL code) is immutable and cannot be changed.

**Optimistic Locking:** Client must send `version`; mismatch returns `VERSION_CONFLICT`.

**Validation Rules:**
- Reject `code` mutation.
- Block circular parent assignment.
- Enforce unique name in parent.
- Validate parent eligibility for selected type.

**Request Body:**
```json

  "type": "ACCOUNT",
  "parentCode": "A3004001",
```
